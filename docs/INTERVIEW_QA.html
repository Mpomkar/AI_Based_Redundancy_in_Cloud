1. Project Overview

Q1. What is your project about?
Answer: It is a cloud storage demo that checks uploaded files for duplicates and redundant copies. When a user uploads a PDF, Word file, or image, the system decides whether to store it or reject it. It also shows a risk score and suggestions on the dashboard. The goal is to save storage space by blocking duplicate and near-duplicate files.
Q2. What problem does it solve?
Answer: In cloud storage, people often upload the same file many times, or slightly changed versions of the same document. That wastes space and money. Our system finds exact copies and very similar files automatically, so storage stays clean and optimized.
Q3. What technologies did you use?
Answer:
  • Frontend: React, TypeScript, Vite, Recharts
  • Backend: FastAPI (Python), SQLAlchemy, SQLite
  • ML: scikit-learn (Logistic Regression)
  • File processing: pypdf, python-docx, Pillow, ImageHash
  • Auth: JWT tokens, bcrypt password hashing
Q4. What happens when a user uploads a file? (Short flow)
Answer: File is uploaded → SHA-256 hash checked → if not exact duplicate, content similarity is calculated → 3 features are built → Logistic Regression predicts redundancy → policy rules + ML rules decide store or reject → result and risk score shown on dashboard → event saved in database.
Q5. What file types are supported?
Answer: PDF, Word (.docx), and images (JPEG, PNG, WebP, GIF). Other types are rejected with an error message.

2. SHA-256 & Duplicate Detection

Q6. What is SHA-256 and why do you use it?
Answer: SHA-256 is a hashing algorithm. It converts any file into a fixed 64-character fingerprint. If two files have the same hash, they are byte-for-byte identical. We use it because it is fast, reliable, and perfect for catching exact duplicates before doing slower content analysis.
Q7. Is SHA-256 part of AI?
Answer: No. SHA-256 is a deterministic mathematical function, not machine learning. Same input always gives same output. There is no training or prediction — just hashing and comparison.
Q8. Can we detect redundancy without SHA-256?
Answer: Partially yes. We can still find similar files using Jaccard similarity (documents) and pHash (images), plus ML. But without SHA-256, catching exact duplicates becomes slower (byte-by-byte comparison) or less reliable. SHA-256 is the best first step for identical files.
Q9. What is the difference between exact duplicate and near-duplicate?
Answer:
  • Exact duplicate: Every byte is the same. Detected by SHA-256. Decision: rejected_duplicate.
  • Near-duplicate: Content is very similar but not identical (e.g. edited report). Detected by Jaccard/pHash + ML. Decision: rejected_redundant.
Q10. What if someone renames a file and uploads again?
Answer: If the file content is exactly the same, SHA-256 will still match — filename does not matter. The hash is computed from file content, not the name.

3. Similarity Algorithms

Q11. How do you compare PDF and Word documents?
Answer: We extract text from the uploaded file and from stored files. Then we use Jaccard word similarity: we split text into words, make two sets, and calculate common words ÷ total unique words. Higher score = more similar documents.
Q12. What is Jaccard similarity in simple words?
Answer: Imagine two bags of words. Jaccard similarity = (words in both bags) divided by (all unique words in either bag). If two documents share 85 out of 100 unique words total, similarity is 0.85 (85%).
Q13. How do you compare images?
Answer: We use perceptual hash (pHash). It creates a fingerprint based on how the image looks, not exact pixels. Similar images get similar hashes even after small changes like resize or compression. We compare hashes using Hamming distance and convert that to a similarity score.
Q14. What is the 92% policy threshold?
Answer: It is a business rule. If content match is 92% or higher, the file is rejected as a near-duplicate even before ML decides. Default is 92% but it can be changed in the .env file. This is a rule, not AI.
Q15. What is “neighbor frequency”?
Answer: It counts how many stored files have similarity ≥ 55% with the new upload. If many files are similar, the new file is more likely redundant. This count is one of the 3 ML input features.

4. AI / Machine Learning

Q16. Where is AI used in your project?
Answer: AI is used in one place: Logistic Regression from scikit-learn. It predicts the probability that a file is redundant (0 to 1). Everything else — SHA-256, Jaccard, pHash, policy rules — is classical programming, not machine learning.
Q17. What is Logistic Regression in simple words?
Answer: It is a machine learning model that takes numbers as input and outputs a probability between 0 and 1. Here, 0 means “probably not redundant” and 1 means “probably redundant.” It learns from training data by adjusting weights on each feature.
Q18. What are the 3 features fed to the ML model?
Answer:
FeatureMeaning
max_similarityBest match score (0–1) against stored files
size_ratioSmaller file size ÷ larger file size (vs best match)
neighbor_frequencyHow many similar files exist (≥55%), scaled 0–1
Q19. How is the model trained?
Answer: On first startup, if no model file exists, the system creates 4,000 synthetic (fake) examples with hand-written rules and trains Logistic Regression on them. The model is saved as backend/models/redundancy_model.joblib. It is not trained on real user uploads in this demo.
Q20. Why synthetic data instead of real uploads?
Answer: This is a demo/project. Real uploads may not have enough labeled examples at start. Synthetic data lets the model work immediately without waiting for hundreds of labeled files. In production, you would retrain on real labeled data for better accuracy.
Q21. What does the dashboard model dropdown do (Random Forest, Neural Network, etc.)?
Answer: In the current project, it is UI only. The backend always uses Logistic Regression. The dropdown is for future extension — multiple models are not implemented yet.
Q22. How is the risk score calculated?
Answer: It combines ML probability and similarity:
risk = 0.45 × ML_prob + 0.35 × max_similarity + 0.20 × (ML_prob × max_similarity)
Then multiply by 100 to get 0–100%. High = 66%+, Medium = 34–65%, Low = below 34%.
Q23. When is a file finally rejected?
Answer: A file is rejected if any of these is true:
  • SHA-256 matches an existing file (exact duplicate)
  • Content match ≥ 92% (policy threshold)
  • Similarity ≥ 96%
  • ML probability ≥ 88% AND similarity ≥ 40%
  • ML probability ≥ 62% AND similarity ≥ 50%
Q24. Why use ML if you already have similarity and rules?
Answer: Similarity alone cannot capture all patterns. ML combines multiple signals — similarity, file size, and how many neighbors are similar — into one probability. Rules handle clear cases; ML helps with borderline cases where simple thresholds are not enough.

5. Architecture & Tech Stack

Q25. Explain frontend and backend communication.
Answer: React frontend runs on port 5173. Vite proxies /api requests to FastAPI on port 8000. Frontend sends JWT token in the Authorization header. Backend validates token and returns JSON responses.
Q26. Why FastAPI instead of Flask or Django?
Answer: FastAPI is modern, fast, has automatic API documentation (/docs), built-in data validation with Pydantic, and good async support for file uploads. Good choice for REST APIs.
Q27. Which database tables do you have?
Answer:
  • users — accounts, roles (admin/user), passwords (hashed)
  • stored_files — files that were accepted and saved
  • upload_events — every upload attempt (stored or rejected) for analytics
Q28. Where are uploaded files stored physically?
Answer: On disk under backend/storage/uploads/{user_id}/. Metadata (hash, similarity, risk) is in SQLite. Files are served via /static/uploads.
Q29. What is the main file that runs the upload pipeline?
Answer: backend/app/services/process_upload.py — function process_upload(). It orchestrates hashing, similarity, ML, decision, and database save.

6. Users, Roles & Security

Q30. What is the difference between Admin and User?
Answer:
  • Admin: Sees global dashboard, all uploads/stats, can create/manage/delete users.
  • User: Uses the portal — upload files and see only their own duplicates and stats.
Each user’s files are checked only against their own library, not other users’ files.
Q31. How does login and authentication work?
Answer: User sends username/password to /api/auth/login. Backend verifies with bcrypt, returns a JWT token. Frontend stores token in localStorage and sends it with every API request. Protected routes check the token before allowing access.
Q32. What is JWT?
Answer: JWT (JSON Web Token) is a secure token that proves the user is logged in. It contains user id, username, role, and expiry time. Backend signs it with a secret key so it cannot be faked easily.
Q33. Why hash passwords with bcrypt?
Answer: Passwords must never be stored in plain text. bcrypt converts password into a one-way hash that is slow to compute — this makes brute-force attacks harder. We only compare hashes at login, never store raw passwords.

7. Scenario-Based Questions

Q34. User uploads the exact same PDF twice. What happens?
Answer: First upload: stored (if not similar to anything else). Second upload: SHA-256 matches the first file → immediately rejected as rejected_duplicate, risk 100%, no ML needed.
Q35. User uploads a report that is 89% similar to an old report. What happens?
Answer: SHA-256 different → similarity scan finds 89% Jaccard match → features built → ML gives high redundancy probability → if ML rules trigger (e.g. prob ≥ 62% and sim ≥ 50%), file is rejected_redundant. Policy 92% does not reject (89 < 92).
Q36. Two different users upload the same file. Is the second rejected?
Answer: No — not in our project. Each user has a separate file library. User B’s upload is compared only to User B’s stored files, not User A’s. This is by design for multi-user privacy.
Q37. What improvements would you make in production?
Answer: Train ML on real labeled data; add Alembic migrations; use PostgreSQL instead of SQLite; wire up multiple ML models; add cloud storage (S3/Azure); rate limiting; stronger JWT secret from environment; optional global dedup across organization; unit and integration tests.
Q38. What are limitations of your project?
Answer:
  • ML trained on synthetic data, not real uploads
  • Model dropdown on UI is not connected to backend
  • Per-user dedup only (not organization-wide)
  • SQLite — not ideal for very large scale
  • Text extraction from PDF may miss scanned/image PDFs
